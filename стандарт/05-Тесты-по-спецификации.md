# Тесты по спецификации

\# Тесты на правила не пишет ни человек, ни ИИ: их порождает генератор из текста спецификации при каждом прогоне. Ожидаемый результат каждого теста вычисляется исполнением самой спецификации, поэтому тест нельзя подогнать под код.

## Что порождается

| Таблица | Тест |
|---|---|
| Реквизиты | Объект создаётся ровно с этими реквизитами, с их типами, обязательностью и значениями по умолчанию, и читается без потерь |
| Перечисление | В коде те же значения в том же порядке |
| Таблица решений, строка i | Состояние, где условия строк выше ложны, а условие строки i истинно; вызов метода; сравнение реквизитов и ответа с тем, что даёт интерпретатор; для `Ошибка «текст»` — ожидание отказа с этим текстом |
| Таблица шагов | Прогон, где выполняются все шаги; по прогону, где пропущен только шаг с условием, для каждого такого шага; для каждого шага, перед которым есть шаг с компенсацией, — прогон со сбоем на нём: реквизиты и вызовы после компенсаций и проброшенный сбой |
| Примеры | Те же проверки, что для строки правила, но на заданном входе |
| Ограничения и инварианты | Для метода, который меняет реквизит из ограничения или условия инварианта, — по тесту на каждое правило, которое метод может нарушить: вход, на котором после метода правило нарушилось бы; ожидается `Ошибка «текст»` правила и неизменные реквизиты ([Типы: Ограничения и инварианты](03-Типы.md#Ограничения%20и%20инварианты)) |
| Техническое соответствие | Класс есть в модуле; внешний объект заменяется регистратором, и проверяются его вызовы |

| Правило | Как выполнять | Проверка |
|---|---|---|
| ИмяТеста | `test_<Объект>_<Метод>_<Правило>`; у таблиц данных — `test_<Объект>_<Раздел>`; у примеров — суффикс `_примерN`; у шагов — `_ВсеШаги`, `_Без<Правило>`, `_СбойНаШаге<N>`; у охраны — `_Нарушение<Реквизит>`, с номером условия, если их у реквизита несколько (`_НарушениеВозраст2`), и `_Нарушение<Правило>` для инварианта. Имя уникально в проекте | Генератор |
| Группы | Тесты сгруппированы, как `describe` в других фреймворках: класс `Тест_<Объект>` для таблиц данных и класс `Тест_<Объект>_<Метод>` для каждого метода. Описание класса — объект или заголовок метода | Генератор |
| Описание | У каждого теста описание из трёх строк, на языке спецификации: правило и его строка («ЗакрытиеЗакрытой: если Статус = Закрыта → Ошибка «Задача уже закрыта»»), вход, который подобрал генератор, и результат, который вычислила спецификация. Первую строку `unittest -v` печатает рядом с именем теста и при падении, так что владелец видит, какое правило нарушено, не читая кода | Генератор |
| НеПравитьРуками | Файл сгенерированных тестов не правится: при каждом прогоне CI он порождается заново из спецификации | Нет |
| ВыборВхода | Если для теста таблицы шагов подходит несколько входов, генератор берёт тот, где условие шага перед ним не такое, как на входе (его меняют предыдущие шаги), и где оно стоит на границе: сдвиг числа из условия на 1 меняет исход. Так тест ловит код, который проверяет условие не в тот момент или путает `≥` и `>` | Генератор |
| СостояниеНеПодобрано | Если генератор не подобрал состояние для строки, он падает и называет строку; выход — таблица [Примеры](04-Методы.md#Примеры) | Генератор |

## Тестовая обвязка

\# Единственный тестовый код, который пишется руками или ИИ: как создать объект, прочитать его реквизиты и вмешаться в окружение. Ожидания в тестовой обвязке не живут, поэтому кривая тестовая обвязка даёт красный CI на настоящих правилах, а не зелёный на пустых тестах.

| Функция | Что делает |
|---|---|
| `создать(Объект, значения)` | Создаёт объект класса `Объект` с заданными реквизитами; значения перечислений приходят именами, ссылки — созданными объектами или регистраторами |
| `прочитать(объект)` | Возвращает реквизиты объекта словарём: значения перечислений — именами, объекты по ссылке — вложенными словарями, внешние объекты пропускаются |
| `класс(Объект)` | Класс объекта или перечисления в коде |
| `значения_перечисления(Имя)` | Имена значений перечисления в порядке кода |
| `сейчас(момент)` | Подменяет `Сейчас` для кода |
| `сбой_на_шаге(Объект, Метод, N)` | Контекст, в котором шаг N метода падает с исключением `Сбой` |
| `внешний(Объект)` | Регистратор вместо внешнего объекта: запоминает вызовы в `вызовы` как пары (метод, параметры) |

| Исключение | Когда возникает |
|---|---|
| `Сбой` | Его бросает подменённый шаг внутри `сбой_на_шаге`; метод передаёт его дальше после компенсаций |

| Правило | Как выполнять | Проверка |
|---|---|---|
| ТолькоКонструирование | Тестовая обвязка создаёт, читает и подменяет окружение; она не проверяет поведение и не знает правил | Нет |
| ШагиВКоде | Чтобы `сбой_на_шаге` работал, шаги метода в коде отделимы: например, каждый шаг — свой метод, который тестовая обвязка может подменить. Как именно — решает проект в тестовой обвязке | Нет |

## Дополнительные тесты

| Правило | Как выполнять | Проверка |
|---|---|---|
| ВнутреннийТест | Тест инфраструктуры или внешнего сервиса, написанный руками, помечается `@internal("причина")`; это отделяет его от тестов правил | Нет |
| ТестКПравилу | Тест, написанный руками сверх сгенерированных (редкий случай: то, что перебором не достать и примером не задать), помечается `@spec("Объект#Правило")`. В этой версии генератор пометку не проверяет | Нет |

## Покрытие кода

\# Обратная сторона покрытия правил: непокрытая строка кода — это код без правила.

| Правило | Как выполнять | Проверка |
|---|---|---|
| ПорогПокрытия | Прогон тестов падает, если доля строк кода, выполненных тестами, ниже порога. Порог хранится в одном файле проекта и только растёт: если покрытие выросло, порог поднимают в том же изменении | Проверка в CI |
