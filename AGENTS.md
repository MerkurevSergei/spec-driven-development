# Правила работы над репозиторием

Для людей и ИИ-агентов, которые меняют стандарт, генератор или пример. Как подключить стандарт к своему проекту — в [Подключение-к-проекту.md](Подключение-к-проекту.md).

## Задачи живут в issues

| Правило | Как выполнять |
|---|---|
| КаждыйПунктОтдельно | Каждая находка, вопрос или предложение — отдельный issue в GitHub. Не список в одном issue, не заметка в чате или в стороннем документе |
| БезПовторов | Перед новым issue найти похожий. Если он есть — дописать комментарий к нему |
| Самодостаточность | Issue читается без ревью, чата и памяти о прошлых разговорах: что, где, на примере и что предлагается |
| Связи | Связанные issues называются номером: «Связано: #22». Если два issue предлагают противоположное — сказать это в обоих |

Разделы issue, по порядку:

| Раздел | Что в нём |
|---|---|
| Где | Файл и правило: `стандарт/04-Методы.md`, правило `Ответ` |
| Что сейчас | Текст правила дословно, если issue о формулировке |
| Что не так | Одно-два предложения: что ломается и у кого |
| Пример | Кусок документа объекта с шапками всех таблиц; строка `Внешний \| Да` — если объект внешний. Заголовок объекта, комментарий о назначении и строку `Модуль` можно опустить, для прогона их добавляют |
| Вывод генератора | Версия и то, что напечатал генератор: ошибку или порождённый тест. Пример перед этим прогнан на текущей версии |
| Что предлагается | Правка стандарта «было → стало» и правка генератора. Если вариантов несколько — все, с меткой `решение` |
| Источник | Откуда пункт: ревью, проба, проект |

Пишется словами стандарта: «Действия», «Ответ», `Ошибка «текст»`. Своих терминов не вводить.

## Метки

| Метка | Когда |
|---|---|
| стандарт | Правится текст стандарта |
| генератор | Правится генератор |
| пример | Правится `пример/` |
| решение | Нужен выбор владельца; варианты перечислены в issue |
| важно | Верный код красный, неверный зелёный или правило пропадает молча |
| средне | Спецификацию нельзя записать или генератор падает без места |
| мелочь | Формулировка, порядок разделов, описание теста |

У issue одна метка веса и сколько нужно меток вида.

## Порядок работы

| Шаг | Что делать |
|---|---|
| 1. Показать | Правку стандарта показать в issue или в чате как «было → стало», с примером из issue |
| 2. Ждать «ок» | Стандарт и код менять только после «ок» владельца. Для `решение` — после выбора варианта; выбор записать комментарием в issue |
| 3. Ветка и PR | Одна тема — одна ветка и один PR. В описании PR — `Closes #N` для каждого закрываемого issue |
| 4. Проверить | Перегенерировать тесты примера и прогнать их; прогнать пример из issue и показать новый вывод |
| 5. CHANGELOG | Если меняется стандарт, генератор или пример — запись в [CHANGELOG.md](CHANGELOG.md) с номером issue: «… (#4)». Если спецификации требуют правок — раздел «Как перейти» |
| 6. Влить | PR вливает владелец или агент с его «ок». Тег версии ставит владелец |

Проверка примера:

```sh
python -m генератор пример/спеки пример/tests/test_по_спецификации.py
cd пример && python -m unittest discover -s tests -t .
```

Версия растёт по таблице «Версии» в [README.md](README.md).

## Стиль

| Правило | Как выполнять |
|---|---|
| Язык | Русский, коротко, полными предложениями |
| Таблицы | Правила, сравнения и варианты — таблицей, а не абзацами |
| Примеры | С шапками таблиц: читатель не помнит контекст |
