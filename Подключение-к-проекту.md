# Подключение к проекту

\# Как подключить стандарт к проекту через git и настроить CI так, чтобы тесты, сгенерированные по спецификации, проходили вместе с кодом. Примеры — для Python и GitHub Actions; для другого стека меняются только команды.

## Схема

| Что | Где в проекте | Кто пишет |
|---|---|---|
| Стандарт | `docs/стандарт-спецификаций/` — git submodule на тег этого репозитория | Не правится в проекте |
| Спецификации | `docs/specs/` — по документу на объект, по правилам стандарта | Владелец вместе с ИИ |
| Предлагаемые изменения | `docs/specs/предлагаемые-изменения/` | Владелец вместе с ИИ |
| Тесты правил | `tests/` — каждый тест помечен ссылкой на правило с хэшем | ИИ по спецификации |
| Парсер спецификаций | `tests/test_спецификации.py` — тест в наборе проекта | ИИ по стандарту |
| Порог покрытия | `порог-покрытия.txt` в корне — одно число, процент строк | Только растёт |

## Подключение стандарта

\# Из корня проекта. Адрес — SSH; если CI ходит по HTTPS, используйте `https://github.com/MerkurevSergei/spec-driven-development.git`.

```bash
git submodule add git@github.com:MerkurevSergei/spec-driven-development.git docs/стандарт-спецификаций
git -C docs/стандарт-спецификаций checkout v0.1.0
git add .gitmodules docs/стандарт-спецификаций
git commit -m "docs: стандарт спецификаций v0.1.0"
```

| Действие | Команда |
|---|---|
| Клонировать проект вместе со стандартом | `git clone --recurse-submodules <адрес проекта>` |
| Подтянуть стандарт в уже склонированный проект | `git submodule update --init` |
| Перейти на новую версию | `git -C docs/стандарт-спецификаций fetch --tags && git -C docs/стандарт-спецификаций checkout v0.2.0`, затем коммит изменения submodule. Перед переходом прочитать [CHANGELOG](CHANGELOG.md) |

\# В AGENTS.md (или CLAUDE.md) проекта добавьте строку: «Спецификации в `docs/specs/` пишутся по стандарту `docs/стандарт-спецификаций/стандарт/00-Обзор.md`; изменил поведение — сначала спецификация, потом тест и код».

## Тесты по спецификации

\# Каждое правило спецификации связано с тестом в обе стороны ([Покрытие тестами](стандарт/05-Покрытие-тестами.md)). ИИ генерирует тест по строке правила и ставит пометку `Объект#Правило~хэш`; имя теста вписывается в колонку `Тест` правила.

| Шаг | Что делать |
|---|---|
| Новое правило | В колонке `Тест` — `ТребуетсяТест`. CI красный, пока теста нет |
| Генерация теста | ИИ пишет тест по строке правила, помечает его `@spec("Объект#Правило~хэш")` и заменяет `ТребуетсяТест` именем теста |
| Правка правила | Хэш строки меняется, CI падает на `test_хэш_устарел` и печатает новый хэш. Тест пересматривают и вписывают новый хэш |
| Тест без правила | Инфраструктура и внешние сервисы — пометка `@internal("причина")`. Тест без пометки — ошибка |

\# Пометки для Python — файл `tests/spec.py`:

```python
def spec(ref):
    """Связывает тест с правилом спецификации: "Объект#Правило~хэш"."""
    def wrap(test):
        test.spec_ref = ref
        return test
    return wrap


def internal(reason):
    """Тест без правила спецификации; причина обязательна."""
    def wrap(test):
        test.spec_internal = reason
        return test
    return wrap
```

\# Хэш правила по [Покрытие тестами: Хэш правила](стандарт/05-Покрытие-тестами.md#Хэш%20правила); ячейки уже нормализованы (от ссылки — текст, без обратных кавычек, пробелы схлопнуты), у строки таблицы решений впереди идут условия строк выше:

```python
import base64
import hashlib


def хэш_правила(ячейки: list[str]) -> str:
    строка = " | ".join(ячейки)
    return base64.b32encode(hashlib.sha256(строка.encode("utf-8")).digest()).decode().lower()[:8]
```

## Парсер спецификаций

\# В версии 0.1.0 парсер не поставляется: проект держит его в своём наборе тестов (`tests/test_спецификации.py`), ИИ генерирует его по стандарту. Парсер читает `docs/specs/`, находит тесты по пометкам `spec_ref` и `spec_internal` и падает с понятным сообщением.

| Проверка | Правила стандарта |
|---|---|
| Оформление документов | Тесты из колонки `Тест` частей [Оформление](стандарт/01-Оформление.md), [Документ объекта](стандарт/02-Документ-объекта.md), [Типы](стандарт/03-Типы.md), [Методы](стандарт/04-Методы.md) |
| Связь правил и тестов | `test_нет_теста`, `test_тест_не_найден`, `test_правило_не_найдено`, `test_отметка_забыта`, `test_тест_без_спеки`, `test_дубли` |
| Актуальность тестов | `test_хэш_устарел` |
| Имена в коде | `test_имена_в_коде` |
| Предлагаемые изменения | `test_формат_изменения` |

## CI

\# Пример для GitHub Actions — файл `.github/workflows/tests.yml`. CI зелёный, только когда спецификация, код, тесты и порог покрытия совпадают.

```yaml
name: Тесты по спецификации

on:
  pull_request:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          submodules: true        # без этого стандарта в CI не будет
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - name: Зависимости
        run: pip install -r requirements.txt coverage
      - name: Тесты и парсер спецификаций
        run: coverage run -m unittest discover -s tests
      - name: Порог покрытия
        run: coverage report --fail-under="$(cat порог-покрытия.txt)"
```

| Ситуация | Что сделать |
|---|---|
| Репозиторий стандарта приватный | Добавьте в проект секрет с ключом доступа на чтение и передайте его в `actions/checkout` (`ssh-key:` или `token:`). Для публичного репозитория ничего не нужно |
| Покрытие выросло | Поднимите число в `порог-покрытия.txt` в том же изменении |
| CI упал на `test_хэш_устарел` | Пересмотрите тест под новую редакцию правила и впишите напечатанный хэш |
